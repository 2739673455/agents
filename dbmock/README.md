# dbmock

为 `insight` 构造一个中国中小型综合电商平台规模的两年期 Doris 数仓

## 数据目标

- 数据截止时间取任务实际开始执行时的 `Asia/Shanghai` 业务日期
- 默认开始日期为截止日期向前两个自然年，首尾日期均包含
- 商品目录使用国内公开电商页面的真实商品数据
- 用户、流量、交易、营销和库存按真实业务分布生成
- 会话、搜索、加购、订单、支付、履约、退款和库存使用同一条业务时间线
- 跨日和跨月事件到实际发生日期后才写入 Doris，截止时刻保留未完成业务
- 日期维度通过 `chinese-calendar` 使用国务院公布的法定节假日和调休工作日安排，运行区间超出依赖支持年份时直接报错，不按周末规则猜测
- 历史事实的入仓时间根据业务发生时间和处理延迟生成，不统一使用任务执行时间
- 外部页面没有公开的字段不伪装成采集值，平台内部成本和库存等字段使用明确的业务生成模型

## 当前数据规模

真实商品目录包含：

- 5,000 个 SPU
- 28,668 个真实 SKU
- 520 个类目

## 真实数据与生成数据边界

真实采集字段包括：

- 商品标题、品牌、店铺、来源类目和公开商品参数
- SPU 与 SKU 关系、SKU 规格、售价、划线价和图片
- 外部商品 ID、外部 SKU ID、来源链接和采集时间

平台标准化字段包括：

- 内部 SPU、SKU、品牌、类目、商家和店铺业务 ID
- 平台三级类目和品牌名称归一结果

业务生成字段包括：

- 用户、用户标签和用户等级变化
- 商品上架时间、历史价格轨迹和标准成本
- 活动窗口、优惠券窗口和适用范围
- 会话、浏览、搜索、点击、收藏和加购
- 订单、支付、物流、退款和评价
- 初始库存、预占、释放、出库、退货入库和采购补货

这些字段不是外部平台采集记录，但必须满足真实业务的时间顺序、金额关系、状态流转和库存连续性

当前已知的真实性问题、修改优先级和验收标准见 [REALISM_ROADMAP.md](REALISM_ROADMAP.md)

## 生成架构

数仓包含 46 张业务表，生成检查点不进入 Doris

生成过程分为两层批次：

- 业务月份批次负责时间演化、状态继承和失败恢复
- 每 250,000 行的 PyArrow Parquet Stream Load 批次负责物理写入 Doris
- 每个月结束后按表使用 4 个工作线程并发写入，单个表内部仍保持顺序

Parquet 使用 Snappy 压缩并开启 Doris 严格模式。并发只改变物理装载方式，不改变业务时间演化、随机种子、表粒度或跨表关联

完整生成流程：

```text
初始化日期、地区、用户和真实商品维度
  ↓
初始化具有独立活动窗口和适用范围的营销规则
  ↓
按业务月份推进
  ↓
按天生成价格事件
  ↓
会话 → 浏览 → 搜索 → 点击 → 加购 → 订单
  ↓
支付 → 库存预占 → 发货出库 → 签收 → 退款或评价
  ↓
未来事件进入待处理队列，到实际业务日期后写入
  ↓
采购补货和退货入库
  ↓
将当月库存事件写入 Doris
  ↓
Doris 按集合计算生成库存日快照
  ↓
保存月末检查点并进入下个月
```

商品不会同时在第一天上架。平台初期保留一部分存量商品，其余商品在两年内逐步上架，库存日快照只覆盖当日已经上架的 SKU

SKU 新品标识根据上架日期计算，热销状态根据订单日汇总计算，库存预警阈值保存在 SKU 拉链维度。这些属性不再重复保存为逐 SKU 的运营日快照

商品历史价格从内部上架价格逐步演化，在采集日期附近与真实采集价格衔接。标准成本根据稳定的品类毛利区间生成，因此订单成本、库存成本和毛利分析不再全部为 0

初始库存按 SKU 分布生成，不再固定为每个 SKU 100,000 件。生成期间根据预计销量、现有可用库存和预警库存创建采购补货事件

## 月度检查点

`data/generation_checkpoint.json` 保存：

- 逻辑运行 ID
- 业务月份
- 批次状态
- 月末 SKU 库存状态
- 待处理的跨日跨月业务事实
- 待处理的跨日跨月库存事件
- 用户累计订单次数
- 各表累计生成数量

逻辑运行 ID 由数据起止日期、商品目录哈希和生成模型配置哈希确定，每次程序执行使用独立的 Stream Load ID

月份执行前写入 `RUNNING`，成功后覆盖为 `COMPLETED`。月份中途失败后，再次执行相同命令会从最近一个已完成月份恢复，并通过业务表 UNIQUE KEY 重放失败月份

检查点采用同目录临时文件加原子替换写入，只在最新完成位置保存一份完整业务状态，避免每个月重复保存全部 SKU 库存。该文件属于本地运行状态，不进入 Git，也不作为数仓业务数据

初始化基础维度期间失败时应重新执行 `make init_db`。业务月份开始后不再要求失败时清空整个数据库

## 本地性能

以下数据是跨月待处理事实改造前的历史性能基准。模型版本 2 会减少截止时刻之后的事实，并在本地检查点保留未完成事件，完成新一轮全量构建后需要重新记录基准：

| 项目 | 实测值 |
| --- | ---: |
| `make generate` 总时间 | 6 分 08 秒 |
| 最终业务表行数 | 21,947,955 |
| Python 进程峰值内存 | 1.90 GiB |
| 最终质量校验 | 46 张表全部通过 |

该时间不包含 `make init_db`。普通月份约 11～16 秒，其中业务数据计算约 3～6 秒，并发 Parquet 写入约 8～10 秒，Doris 库存快照约 0.3～1 秒。日志会输出每月总耗时、生成耗时、写入耗时、快照耗时、Stream Load 次数和 Parquet 大小

耗时会受 CPU、磁盘、Doris 容器资源和已有系统负载影响，但默认规模已经按本地 10 分钟内完成全量构建进行验证

## 审计时间

- 事务事实根据事件时间模拟分钟级处理延迟
- 日快照根据每日期末时点模拟小时级处理延迟
- 维度根据生效时间或来源更新时间生成入仓时间
- 所有业务时间和入仓时间均不晚于任务实际开始时刻
- `load_batch_id` 使用逻辑运行 ID 和业务月份
- 跨月事实使用实际事件发生月份的 `load_batch_id`，不使用订单创建月份

## 环境要求

- Python 3.12 及以上版本
- `uv`
- Apache Doris 4.0 及以上版本
- dbmock 主机可以访问 Doris FE 的 `9030`、`8030` 端口和 BE 的 `8040` 端口

初始化项目环境：

```bash
cd dbmock
cp .env.example .env
uv sync
```

数据库连接从 `.env` 读取且没有默认值：

```dotenv
DB_HOST="127.0.0.1"
DB_PORT=9030
DB_USER="root"
DB_PASSWORD=
DB_NAME="ecommerce"
```

Stream Load 的 FE HTTP 端口在 `src/settings.py` 中固定为 `8030`

## 使用流程

### 准备真实商品目录

新环境执行完整采集：

```bash
uv run python -m collection
```

只校验现有目录：

```bash
uv run python -m collection --validate-only
```

强制清空采集断点并重新采集：

```bash
uv run python -m collection --force-download
```

`data` 不进入 Git，完整目录包括：

```text
data/
├── manifest.json
├── brands.json
├── categories.json
├── shops.json
├── spus.jsonl
├── skus.jsonl
├── lineage.jsonl
├── geo_regions.json
├── logistics_companies.json
├── payment_types.json
├── generation_checkpoint.json
└── source/
```

### 初始化 Doris

```bash
make init_db
```

该命令会永久删除并重建 `.env` 中 `DB_NAME` 指定的数据库，清理本地生成检查点，然后创建 46 张业务表

### 生成数据

完整生成：

```bash
make generate
```

相同执行日期和商品目录下再次运行 `make generate` 会从月度检查点继续

生成模型版本或配置哈希变化后必须重新执行 `make init_db`，不能在旧检查点和旧业务表上继续生成

七天小规模验证：

```bash
make init_db
make smoke
```

只加载公共维度和商品维度：

```bash
make init_db
uv run main.py --dimensions-only
```

只校验已有数据：

```bash
make validate
```

## 质量校验

完整任务结束后检查：

- 必填业务表非空以及未知维度成员完整
- SCD2 生效区间不重叠且只有一个当前版本
- SPU、SKU、品牌、类目和店铺引用完整
- 每条订单明细可以追溯到来源会话和同会话加购事件
- 订单活动优惠和优惠券金额分摊一致
- 支付金额与订单明细支付分摊一致
- 包裹重量和运费与包裹商品分摊一致
- 退款金额不超过对应订单实付金额
- SKU 价格事件变更前后价格连续
- 库存事件变更前后数量连续且不会出现负库存
- 库存日快照等于当日库存事件处理后的期末状态
- 会话页面访问数和搜索数与事件明细一致
- 事实业务日期、事件时间和入仓时间顺序正确
- 订单、支付、配送和退款状态时间严格递增
- 事实业务月份与 `load_batch_id` 月份一致
- 历史数据入仓时间不会全部集中在任务执行日期
