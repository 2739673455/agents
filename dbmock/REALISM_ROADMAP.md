# dbmock 数据真实性整改路线

## 目标和判断标准

dbmock 的商品目录允许使用公开页面采集数据，用户、流量、交易、履约和库存只能生成合成数据。真实性目标不是把合成数据描述成真实记录，而是同时满足以下要求：

- 采集字段能够回溯到原始页面，不混入页面控件或猜测值
- 派生字段和生成字段具有明确血缘，不冒充采集字段
- 业务事件只在实际发生时间之后入仓，截止时刻保留未完成状态
- 数量、金额、状态、库存和维度版本能够跨表闭环
- 分布、季节性、长尾和异常情况接近真实中小型综合电商平台

优先级按照错误对分析结论的破坏程度排列，同一优先级内按实施顺序执行。

## P0：必须先解决

### P0-1 跨月和截止时点语义

状态：已完成，版本 3 两年全量验收通过，存在 9,705 条真实跨月订单状态事件且截止时刻保留 2,038 条未来事实

问题：

- 订单创建月份会提前写入后续月份的发货、签收、退款和评价
- 超过任务截止时刻的事件曾被强制压缩到截止时刻
- 月末数据无法还原当时真实可见的业务状态

方案：

- 使用统一 `ScheduledFact` 队列保存未来支付、优惠券、订单状态、包裹、退款和评价事实
- 每个业务日开始时只释放事件时间已经到达的事实
- 待处理事实随月末 `BusinessState` 写入本地 JSON 检查点
- 库存事件继续使用专用队列，事件到期后先改变库存余额再写库存事实
- 未来事实使用实际发生月份的 `load_batch_id`
- 超过最终截止时刻的事件不写入 Doris，保留为检查点中的未完成业务
- 包裹创建、发货和签收使用严格递增的时间，不再共用同一时刻

验收标准：

- 任意月份完成后不存在 `biz_date` 晚于该月末的事实
- `load_batch_id` 的月份与事实 `biz_date` 月份一致
- 订单、支付、配送和退款状态时间按事件序号严格递增
- 最终日期存在合理数量的待支付、待发货或运输中订单
- Doris 中不存在晚于任务截止时刻的业务时间和入仓时间
- 中断恢复前后生成结果一致

### P0-2 商品采集污染和价格有效性

状态：已完成，5,000 SPU 均具有原始响应归档并通过清洗和目录校验

问题：

- 部分 SKU 名称和规格出现“收藏”“加购”等页面控件文本
- 存在 0.05 元等疑似促销占位价或解析错误价格
- 空规格没有区分单规格商品和采集失败
- 极端高价没有结合类目判断是否合法

方案：

1. 在 `collection/source.py` 保存原始响应、页面 URL、抓取时间和解析器版本
2. 在 `collection/preparation.py` 建立页面控件词、HTML 残片和异常规格清洗规则
3. 按类目建立价格合理区间，不使用一个全局上下限
4. 同时存在当前价、划线价和 SKU 价格时执行交叉校验
5. 单规格商品显式写入标准规格值，解析失败商品进入拒绝清单
6. 对被拒绝商品补采，直到重新满足 5,000 SPU 目标
7. 在 manifest 中记录采纳数、拒绝数、拒绝原因和清洗规则版本

验收标准：

- 商品名和规格中的页面控件词命中数为 0
- 核心字段解析失败的商品不会进入标准目录
- 每个异常价格都有源页面证据或被拒绝
- 随机抽样商品能够通过来源链接核对标题、SKU 规格和价格
- 采集清洗结果在相同原始响应和解析器版本下可复现

### P0-3 字段真实性和血缘边界

状态：已完成，catalog manifest 和质量报告均提供机器可读字段级血缘

问题：真实采集、平台标准化、业务派生和合成生成字段目前主要依赖 README 说明，缺少机器可校验的字段级血缘

方案：

1. 在采集 manifest 中为每个输出字段声明 `observed`、`normalized`、`derived` 或 `synthetic`
2. `lineage.jsonl` 保存外部 ID、原始字段、标准字段、转换规则和采集时间
3. 成本、历史价格、上架时间、库存等生成字段记录模型版本和参数摘要
4. 质量检查禁止 `synthetic` 字段被标记为外部采集值
5. README 只总结边界，manifest 作为可执行的事实来源

验收标准：全部入仓业务字段都能定位到来源字段或生成规则，不存在来源不明字段

## P1：影响经营分布真实性

### P1-1 用户生命周期

状态：已完成，七天 smoke 和两年全量验收通过，窗口内注册用户占比 54.80%，当前用户平均标签数 1.93

问题：两年内没有新增注册用户，用户版本变化和标签关系为固定比例

方案：

- 按月生成新增用户，使用获客增长、活动峰值和自然流失曲线
- 为注册渠道、地区、年龄和设备建立有关联的联合分布
- 用户等级和 SCD2 变化由累计消费、退款和活跃度驱动
- 标签由近 30/90 天浏览、购买品类、价格带和活跃度计算
- 新客、活跃、沉默、召回和流失状态跨月继承

验收标准：

- 每月存在新增、活跃、沉默和流失用户
- 标签数量和分数不再固定
- 用户等级变化能够由历史交易解释
- 用户留存和复购率落入预先定义的中小电商合理区间

### P1-2 流量和搜索行为

状态：已完成，七天 smoke 和两年全量验收通过，全量跳出率 12.96%、搜索无结果率 7.50%、搜索点击率 60.92%

问题：页面路径、PV 数、搜索成功率、关键词和客户端属性过于模板化

方案：

- 使用会话长度分布生成 1～多次访问，保留真实跳出会话
- 使用状态转移概率生成首页、类目、搜索、商品、店铺、购物车和结算路径
- 关键词由商品短标题、品牌、类目、属性词和长尾组合生成
- 引入拼写差异、无结果搜索、搜索改写和多次点击
- 渠道、设备、操作系统、版本和时段使用条件分布
- 转化概率由用户阶段、商品价格、活动、库存和流量来源共同决定

验收标准：

- 存在合理的跳出率、无结果率、点击率和搜索改写率
- 会话长度和页面路径不是少数固定模板
- 自然流量、广告流量和不同终端的转化率存在合理差异
- 搜索词频呈长尾分布

### P1-3 交易、支付、退款和评价

状态：已完成，七天 smoke 和两年全量验收通过，支付成功率 95.95%、退款订单率 7.95%、负向评价率 8.25%

问题：支付方式接近均分，退款原因单一，退款全部成功，评价文案和星级过于集中

方案：

- 支付方式按终端、客单价和用户年龄使用条件权重
- 移除不适合独立综合电商平台的支付方式或显著降低权重
- 支付失败区分余额不足、渠道拒绝、超时和用户取消，并允许重试
- 退款原因按类目、物流时效、质量和用户特征分布
- 增加驳回、撤销、部分退款、退款失败和重新打款
- 评价使用多模板和商品属性组合，覆盖 1～5 星、追评和无文本评价
- 评价概率由签收时长、退款、商品质量和用户活跃度决定

验收标准：

- 支付、退款和评价分布不再由固定单一概率决定
- 退款状态包含合理比例的处理中、驳回和失败
- 评价文本去重率、星级分布和情感分布达到设定阈值
- 截止时刻的交易状态结构符合近期订单的自然未完成比例

## P2：增强维度和运营细节

### P2-1 店铺评分和店铺属性

状态：已完成，未公开评分保持空值并删除店铺评分快照表

问题：店铺评分快照为空，部分店铺缺少地址、开店时间和评分

方案：

- 优先补采公开店铺属性
- 无法公开验证的历史评分不生成伪造值
- 如果评分用于演示，由真实评价聚合生成平台内部评分，并明确标记为派生指标
- 如果短期不需要评分分析，删除空快照表及其上层语义配置

验收标准：店铺评分快照要么具有可解释的数据来源，要么从模型和数仓中删除

### P2-2 仓库和补货模型

状态：已完成，库存守恒、在途和履约仓验收通过，全量采购事件 1,804 条、缺货取消率 1.16%、履约仓不一致 0 条

问题：仓库名称和地址为模板，仓库分配及补货过于确定，几乎没有缺货

方案：

- 根据订单区域和仓库服务范围分仓，不再按店铺 ID 取模
- 使用采购提前期、安全库存、在途库存和供应波动生成补货
- 保留少量缺货、拆单、部分发货和延迟到货
- 仓库位置使用真实行政区划，具体地址保持脱敏或明确为生成值

验收标准：库存仍保持守恒，同时出现合理的缺货率、补货提前期和跨仓履约

### P2-3 品类、品牌和店铺集中度

状态：已完成并通过全量验收，自营商品占比 39.90%，自营订单贡献占比 19.36%

问题：一级品类占比来自固定配额，平台自营商品占比偏高

方案：

- 用采集总体分布和目标平台定位共同确定品类权重
- 品牌、店铺和 SKU 销量分别使用长尾分布，避免共用同一排序
- 自营占比作为显式平台参数，并通过订单贡献而不是商品数单独验收
- 增加节日、季节、品类和地区之间的联动

验收标准：商品供给占比、订单贡献占比和 GMV 贡献占比均符合目标平台画像

## P3：持续验收和防回归

状态：已完成，七天 smoke 和 24,291,117 行两年全量数据均通过，报告写入 `data/quality_report.json`

方案：

- 将源字段完整率、异常价格、控件词、重复文案、无结果率、跳出率、支付率、退款率和状态分布加入 `src/quality.py`
- 为每个指标定义阻断阈值和观察阈值
- 全量任务生成机器可读质量报告，记录样本量、分位数、异常样本和模型版本
- 每次模型版本变化必须执行七天 smoke 和两年全量基准
- 质量报告与商品 manifest 一同保存在 `data`，不写入 Doris 业务表

验收标准：真实性问题能够在自动校验中复现和阻断，而不是依赖人工查看几张表发现

## 推荐实施顺序

```text
P0-1 跨月和截止时点语义
  ↓
P0-2 商品采集污染和价格有效性
  ↓
P0-3 字段真实性和血缘边界
  ↓
P1-1 用户生命周期
  ↓
P1-2 流量和搜索行为
  ↓
P1-3 交易、支付、退款和评价
  ↓
P2 维度及运营细节
  ↓
P3 自动化真实性验收
```

每个阶段完成后先运行七天 smoke，再重新构建两年全量数据。不得在旧检查点上混用不同生成模型版本。
